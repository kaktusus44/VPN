# Две фазы установки

Запускать с управляющей Ubuntu после `scripts/bootstrap-ubuntu-control`.
Существующий формат `scripts/deploy-server main <IPv4>` сохранён.

```bash
# VPN, выдача клиентских данных, затем вопрос о мониторинге
scripts/deploy-server main 1.2.3.4

# Только VPN; в конце останется вопрос об отключении SSH-пароля
scripts/deploy-server --phase core main 1.2.3.4

# Мониторинг позднее, без запуска VPN core и генерации ключей
scripts/deploy-server --phase monitoring main 1.2.3.4

# Только sidecar + интеграция с уже установленными Prometheus/Grafana
scripts/deploy-server --phase exporter main 1.2.3.4

# Для reserve указать main, чтобы разрешить scrape и обновить его Prometheus
VPN_MAIN_IP=1.2.3.4 scripts/deploy-server --phase exporter reserve 5.6.7.8
```

Для reserve мониторинг требует адрес main. Сам VPN можно установить без main.
Inventory создаётся отдельно для каждого сервера:
`inventories/managed/<SSH-IP>/hosts.yml`. Клиентские файлы копируются в
`exports/<SSH-IP>/` с правами каталога `0700` и файлов `0600`. На сервере
сохраняются прежние пути `/var/lib/vpn/`. Эти каталоги исключены из Git.
Ссылки содержат секреты и выводятся в терминал после первой фазы.

## IPv4 и Netplan

Установщик получает все публичные unicast IPv4 из ОС по SSH. Можно указать
дополнительный адрес, **уже прикреплённый к VPS у хостера**. Он записывается
как `/32` в `/etc/netplan/99-vpn-extra-ip.yaml` без gateway/default route.
Существующие Netplan-файлы не редактируются. После `netplan generate`
выполняются `networkctl reload` и `networkctl reconfigure` основного интерфейса.
Проверяются наличие адреса, неизменность default route и маршрут с новым source.
При ошибке файл и конфигурация networkd возвращаются к предыдущему состоянию.

Автоматический режим рассчитан на Ubuntu с Netplan/networkd и однозначно
определяемым ethernet ID основного интерфейса. Для другого renderer, bridge/bond,
NAT-only VPS или нестандартной маршрутизации настройте адрес вручную.
Проверка маршрута не подтверждает, что хостер разрешил исходящий трафик с IP;
это проверяется подключённым клиентом после развёртывания.

При разделении IP входной адрес используется в клиентских ссылках, выходной —
в Xray `sendThrough` и AmneziaWG SNAT. SSH и мониторинг продолжают использовать
первоначальный адрес управления. Без разделения сохраняются прежние
MASQUERADE и выбор исходного IPv4 системой.
При смене выходного IPv4 уже установленные NAT-соединения могут сохранять прежний
адрес до закрытия; проверять новый адрес нужно новым подключением клиента.

Настройки сохраняются на VPS в `/var/lib/vpn/deployment.json`. Повторный запуск
сохраняет число клиентов, ключи, выбранные IP, IPv6-политику и включённые proxy.
Для старой установки без state-файла число клиентов берётся из конфигурации AWG,
а endpoint — из клиентского файла. Изменить решение можно переменными окружения.

## IPv6 и клиентские приложения

По умолчанию пользовательский IPv6 блокируется: Xray использует `ForceIPv4`,
отклоняет IPv6 destinations и получает ограничение семейств адресов в systemd.
Правило UFW блокирует IPv6 forwarding из AWG перед существующими allow-правилами.
Unbound не делает исходящих IPv6-запросов. IPv6 самой ОС глобально не отключается.

Клиентские AWG-конфигурации и `vpn://` сохраняют `::/0` и внутренний IPv6-адрес:
IPv6 попадает в туннель и блокируется сервером, вместо обхода VPN через провайдера.
Клиент должен применять конфигурацию полностью, без split tunneling.

Обычная VLESS-ссылка не может задавать глобальную маршрутизацию приложения.
Для Xray дополнительно выдаётся `xray-tun-client.json` для sing-box **1.12.x**:
TUN захватывает IPv4/IPv6, включает `strict_route`, а DNS идёт через VPN.
Для обычного VLESS-импорта включите в приложении полный TUN/VPN-режим и захват IPv6.
Раздельные приложения, системные исключения и поведение конкретной ОС требуют
проверки на клиенте; одна ссылка сама по себе не гарантирует отсутствие обхода.
При смене IPv6-политики или входного IP импортируйте обновлённые клиентские файлы.

## Xray-exporter

Отдельный systemd-сервис `xray-exporter` на порту `9188` каждые 15 секунд читает
`ss` и PID сервиса Xray. В выборку входят только ESTABLISHED TCP-сокеты этого PID
на VLESS-портах из действующей конфигурации. UUID не используется; общий UUID допустим.
Сервис не меняет конфигурацию Xray, не добавляет API/logging и не перезапускает Xray.

Метрики:

- `xray_tcp_connections{client_ip,asn,provider,inbound_port}` — текущие соединения;
- `xray_tcp_connections_total_current` — их сумма;
- `xray_observer_up`, `xray_observer_last_success_timestamp_seconds` — состояние наблюдения;
- `xray_asn_database_loaded` — доступность локальной базы;
- `xray_observer_dropped_connections` — соединения сверх лимита в 10 000 серий.

Соединения не равны пользователям или аутентифицированным сессиям. XHTTP может
использовать несколько TCP-соединений; сканер может временно попасть в выборку;
короткие соединения между опросами не видны. IP — адрес TCP-peer сервера, который
при наличии внешнего прокси/NAT может отличаться от адреса устройства.
ASN/provider берутся из локальной базы IPtoASN (организация ASN, не всегда бренд ISP).
Клиентские IP не отправляются во внешние lookup API. База IPv4 обновляется общим
таймером `vpn-asn-update.timer`; неизвестные адреса обозначаются `unknown`.

На main exporter слушает loopback. На reserve требуется активный UFW;
доступ разрешается только с адреса main из inventory. Метрики содержат клиентские IP.
При отдельной установке интеграция обновляет только scrape job `xray-exporter`
в существующем Prometheus и кладёт дашборд в существующий каталог managed Grafana.
Если мониторинга ещё нет, запустите вторую фазу. Дашборд: **VPN / Xray connections**.

## SSH

В конце каждой успешно выполненной установки задаётся вопрос об отключении
пароля (по умолчанию нет). Перед изменением проверяются установленный root-ключ
и новое key-only соединение без SSH multiplexing/пароля. Затем устанавливается
`/etc/ssh/sshd_config.d/00-vpn-key-only.conf`, проверяются `sshd -t` и эффективные
настройки для текущего SSH connection context. Выполняется **reload** сервиса `ssh`.
После reload открывается ещё одно независимое соединение по ключу.
При ошибке конфигурация восстанавливается через сохранённое соединение Ansible.
Существующие сеансы не закрываются.

## Автоматизация

```bash
VPN_NONINTERACTIVE=1 \
VPN_CLIENT_COUNT=100 \
VPN_ADDITIONAL_IPV4=5.6.7.8 \
VPN_SPLIT_IP=yes VPN_ENTRY_IPV4=1.2.3.4 VPN_EXIT_IPV4=5.6.7.8 \
VPN_DISABLE_IPV6=yes VPN_INSTALL_MONITORING=no VPN_DISABLE_SSH_PASSWORD=no \
scripts/deploy-server main 1.2.3.4
```

`VPN_PHASE=core|monitoring|exporter|all` эквивалентна `--phase`.
`VPN_SPLIT_IP=no` отменяет разделение, `VPN_DISABLE_IPV6=no` возвращает прежнюю
политику IPv6. `VPN_INSTALL_MTPROTO` и `VPN_INSTALL_SOCKS5` сохранены.
Явный `--phase core` никогда не предлагает установку мониторинга.

Настройки мониторинга и секреты повторного запуска хранятся на VPS в
`/var/lib/vpn/monitoring-settings.json` с правами `0600`. Существующие Basic Auth
файлы сохраняются; для смены пароля передайте `VPN_GRAFANA_BASIC_AUTH_PASSWORD`
и/или `VPN_ALERTMANAGER_BASIC_AUTH_PASSWORD` явно. Пароль Grafana admin после
инициализации БД меняется средствами Grafana, а не повторным deploy.

Обновление apt использует кэш на час; отдельное обновление требуется при добавлении
PPA/Grafana repository. Зависимости сгруппированы, DKMS и скачивание ASN не относятся
к повторным тяжёлым шагам, если уже установлены. Xray перезапускается только после
изменения unit/config. AWG при изменении server config останавливается со **старым**
PostDown, затем запускается с новым config; при ошибке возвращается старый config.
Изменения только клиентских экспортов не перезапускают AWG. MTProto-контейнер
пересоздаётся только при изменении секрета/порта, образ не обновляется на каждом deploy.

## Проверки перед приёмкой нового сервера

```bash
bash scripts/check-local
```

Проверка включает Bash/Ansible syntax и изолированные тесты с подменой SSH,
networkd, генерации ключей и наблюдения соединений. Она не подключается к VPS.
При первой фазе на VPS дополнительно проверяются активность AWG/Xray/Unbound
и наличие клиентских файлов; Xray проверяет новый config до замены файла.

На отдельном тестовом VPS необходимо проверить обе VPN-технологии с реального
клиента: вход на выбранный IPv4, внешний IPv4 равен выходному, IPv6 не выходит
напрямую, DNS работает, ключи не меняются при повторном запуске, unchanged deploy
не меняет PID/время старта сервисов. Затем проверить отдельную вторую фазу,
Prometheus/Grafana, отдельный exporter и key-only SSH после отключения пароля.
Время до выдачи ключей измеряется установщиком, но сравнение скорости требует VPS.
